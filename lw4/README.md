# Экспертный модуль AI-ассистента для личного кабинета платформы онлайн-бронирования отелей

Тема диплома: «Исследование и разработка AI-ассистента для личного кабинета платформы онлайн-бронирования отелей».

Реализован учебный прототип на SWI-Prolog: он диагностирует причины недоступности тарифа для гостя и объясняет рекомендации. Пользователь прототипа — сотрудник отеля, работающий с настройками продаж. Прототип работает локально и не изменяет настройки платформы.

## Постановка задачи для диплома

**Объект исследования:** информационная поддержка сотрудников средств размещения при работе в личном кабинете платформы онлайн-бронирования отелей.

**Предмет исследования:** методы представления знаний и объяснимого логического вывода для диагностики настроек тарифа.

**Цель:** разработать и проверить экспертный модуль, который на основании сведений о тарифе и запросе гостя выявляет известные блокирующие условия, формирует рекомендации и указывает основания решения.

**Задачи:** изучить предметную область; выделить диагностические признаки; формализовать продукционные правила; реализовать механизм вывода и диалог; проверить поведение при полных, неполных и противоречивых данных; определить место модуля в архитектуре AI-ассистента.

Работа представляет учебный прототип экспертного компонента для платформы онлайн-бронирования отелей.

## Границы модели

Одна консультация относится к одному тарифу, одному составу гостей и одному периоду проживания. Смена контекста требует новой консультации. Проверяется доступность тарифа на официальном сайте. Ошибки интеграций, платежных транзакций, браузера и все возможные ограничения не охватываются.

Входные признаки уже нормализованы: например, `rooms_available` означает наличие хотя бы одной подходящей категории с доступностью на каждую ночь. Проверять наличие только на дату заезда недостаточно. `display_period_matches` относится к текущей дате показа, а не к периоду проживания. Сопоставление календарей и вычисление доступности в этом прототипе выполняет человек; автоматический адаптер данных не реализован.

## Состав экспертной системы

| Компонент | Реализация |
|---|---|
| База знаний | `rule/6`, `question/2`, `source/2` |
| Рабочая память | Список `Признак-Значение`, локальный для консультации |
| Механизм вывода | `diagnose/2`, проверка предпосылок правил |
| Объяснение | Идентификатор правила, причина, факты, совет, источник |
| Диалог | `start/0`, вопросы по неизвестным релевантным признакам |
| Проверка входа | Отклонение неизвестных ключей, неверных значений и повторных ключей |

Значения признаков: `yes`, `no`, `unknown`. Пропущенный признак означает `unknown`. Система не использует отсутствие факта как доказательство отрицания. Ввод двух значений одного признака отклоняется, даже если они одинаковы.

## База правил

База содержит учебные правила диагностики настроек тарифа. Приоритеты назначены для удобного порядка рекомендаций и не являются вероятностями.

| Правило | Условие | Вывод |
|---|---|---|
| r01 | `rate_active=no` | Неактивный тариф |
| r02 | `website_enabled=no` | Сайт не подключен |
| r03 | `categories_enabled=no` | Нет активных категорий |
| r04 | `rooms_available=no` | Недостаточная доступность |
| r05 | `sales_open=no` | Продажи закрыты |
| r06 | `payment_available=no` | Нет подходящей оплаты |
| r07 | `guest_matches=no` | Не подходит состав гостей |
| r08 | `display_period_matches=no` | Не подходит время показа |
| r09 | `promo_required=yes` И `promo_valid=no` | Не выполнено условие промокода |
| r10 | `loyalty_required=yes` И `loyalty_matches=no` | Не выполнено условие лояльности |

Закрытый тариф или закрытые продажи могут быть намеренным решением отеля. Поэтому вывод означает блокирующее условие для данного запроса, а не обязательную ошибку настройки.

## Формальная модель и алгоритм

Экспертная система задается как `ES = (F, R, I, E)`, где `F` — факты консультации, `R` — правила, `I` — механизм вывода, `E` — механизм объяснения. Правило имеет форму `c1 ∧ ... ∧ cn → diagnosis` и сопровождается рекомендацией и названием раздела базы правил.

Используется обратный вывод: для каждой возможной причины проверяются все ее предпосылки. Для этой одноуровневой базы достаточно перебрать правила; промежуточные выводы не добавляются в рабочую память. Успешно проверенные правила собираются через `findall/3` и сортируются по приоритету через `keysort/2`. Система возвращает все причины.

Если хотя бы одно условие правила опровергнуто, дополнительные вопросы для этого правила не требуются. Если опровержений нет, неизвестные предпосылки попадают в список недостающих данных. Ответ `unknown` не вызывает повторного вопроса в той же консультации. Порядок вопросов определяется сортировкой имен признаков, а не информационной ценностью.

Результат: `report(Status, Findings, Missing)`.

- `causes_found`: найдена хотя бы одна причина; при непустом `Missing` могут существовать дополнительные причины.
- `insufficient_data`: причин пока нет, но не все потенциально подходящие правила проверены.
- `no_known_cause`: блокировки из этой базы не найдены; доступность в реальной платформе не гарантируется.

Каждый элемент `Findings` имеет вид `finding(Id, Cause, Action, Evidence, SourceRef)`. `Evidence` — предпосылки сработавшего правила, `SourceRef` — название раздела локальной базы правил. Это проверяемая трасса решения, а не сгенерированное языковой моделью обоснование.

## Запуск

Установите [SWI-Prolog](https://www.swi-prolog.org/download/stable). Откройте терминал в папке `lw4`.

```powershell
swipl -q -s hotel_expert.pl -g start -t halt
```

Отвечайте `yes`, `no` или `unknown`, нажимая Enter. Точку после ответа не ставьте. Система дает рекомендации, но не выполняет действия в личном кабинете.

Демонстрация двух причин:

```powershell
swipl -q -s hotel_expert.pl -g demo -t halt
```

Запросы в интерактивной консоли SWI-Prolog:

```prolog
?- [hotel_expert].
?- example(blocked, Facts), diagnose(Facts, Report).
% Status = causes_found; правила r01 и r02; Missing = [].

?- diagnose([rate_active-yes], Report).
% Status = insufficient_data; Findings = [].

?- example(clear, Facts), diagnose(Facts, Report).
% Report = report(no_known_cause, [], []).

?- diagnose([promo_required-yes, promo_valid-no], Report).
% Правило r09; также остается список недостающих данных.
```

Сокращенный пример вывода `demo`:

```text
Статус: causes_found
Правило: r01; причина: inactive_rate
Основание: [rate_active-no]
Совет: Проверьте необходимость активации тарифа.
...
Правило: r02; причина: website_disabled
Основание: [website_enabled-no]
Совет: Проверьте подключение сайта в источниках тарифа.
...
```

## Проверка

```powershell
swipl -q -s hotel_tests.pl -g run_tests -t halt
```

Тесты проверяют множественные причины, неполные данные, конъюнкцию условий, нерелевантность промокода, недопустимый ввод, независимость консультаций и достижимость каждого правила. Они проверяют программную реализацию; подтверждение полноты и точности базы требует отдельной оценки специалистами предметной области.

```powershell
npm.cmd install --prefix .runtime swipl-wasm@8.1.2 --cache .runtime/npm-cache --ignore-scripts --no-audit --no-fund
node --preserve-symlinks --preserve-symlinks-main verify.cjs
```

Для исследования в дипломе можно собрать обезличенные случаи, получить независимую разметку экспертов и измерить precision/recall по причинам, долю случаев с недостатком данных, число уточняющих вопросов и время диагностики. Это план эксперимента: реальные показатели эффективности здесь не заявляются.

## Место в архитектуре AI-ассистента

Предлагаемая архитектура: сообщение пользователя → определение намерения и контекста → получение и проверка фактов → Prolog → причины и доказательства → ответ пользователю.

Prolog реализует символический компонент искусственного интеллекта. Языковая модель могла бы распознавать запрос и формулировать ответ, а модуль поиска по документации — подбирать справочные материалы. Эти компоненты, доступ к API, авторизация и веб-интерфейс в поставку не входят. Неподтвержденные сведения от языковой модели следует передавать как `unknown`. Для интеграции потребуется сохранять источник и время получения каждого факта, а также идентификаторы отеля, тарифа и запроса.

Исследовательский акцент работы — воспроизводимость вывода, объяснимость и работа с неполными данными. Новизну и преимущества перед существующим ассистентом необходимо обосновать сравнительным исследованием.
